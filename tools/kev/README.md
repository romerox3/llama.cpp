# Kev on llama.cpp for Volta GPUs

This branch serves the [Kev](https://github.com/jaredpalmer/kev) decision models (Kev-9B and siblings,
fine-tunes of the hybrid Qwen3.5 Gated DeltaNet + attention architecture) with llama.cpp, as a drop-in
replacement for the reference PyTorch server: same HTTP contract, same answers, faster, and able to take
documents of up to 64k tokens. It builds on [espetro/llama.cpp](https://github.com/espetro/llama.cpp)
(`kev` branch), which ported the Kev decision head to llama.cpp, and was tuned on a single
Tesla V100-SXM2-32GB (sm_70).

## What it adds

HTTP contract, byte for byte with the Python server (`kev/api.py`, `kev/serve.py`):

- confidence of `score` answers, rounding, `usage` (input and output tokens), `model` echo,
  `x-typesafe-request-id` on every response, 422 validation errors, `/v1/models` cards,
  `/v1/systemone/permute` and `/separate`, truncation and the 65,536 / 73,728 token limits;
- checked by C++ contract tests (`tests/test-kev-*.cpp`) against fixtures generated by the original Python
  code (`tools/kev/golden/gen_golden.py`, provenance in `tests/kev/fixtures/PROVENANCE.json`), and by the
  original `tests/test_api.py` run against this server.

Throughput (all flags off by default, so every change was measured A/B with the same binary):

| Flag / variable | What it does |
|---|---|
| `--kev-skip-lm-head`, `--kev-masked-outputs` | no LM head, and only the rows the head reads are outputs |
| `--kev-unified`, `--kev-seq-max N` | unified KV cache: branches share the state cells, many branches per round |
| `--kev-batch N` | the model thread batches up to N queued requests into the same decodes |
| `--kev-prefix-cache N` | LRU cache of decoded document states (repeat questions skip the state) |
| `--kev-pad-branches` | branches of a round padded to one length so the round is one ubatch |
| `--kev-pad-states` | states of different lengths padded into one ubatch: neutral padding (`beta = g = 0` in the delta net, conv window kept at the last real token, causal attention never sees it), trimmed after the decode; grouped by length with a small dynamic program |
| `GGML_CUDA_GDN_CHUNK_VOLTA=1` | upstream PR #26001 (chunked gated delta net) enabled on sm_70: the kernels only use fp16 WMMA and stay under 48 KB of shared memory |
| `GGML_CUDA_GDN_CHUNK_MIN_TOKENS=16` | chunked kernel also for short multi-sequence batches (4+ sequences) |
| `KEV_HTTP_PREP=1` | tokenizing and answer building on the HTTP threads, off the model thread |
| `KEV_HEAD_THREADS=N` | the pointer head of a round on N threads |
| `LLAMA_KEV_KV_SCAN_USED=1` | `seq_rm` / `seq_cp` scan only up to the last used KV cell |
| `LLAMA_KEV_F16_ACT=1` | the normalized input shared by several F16 matmuls is converted to F16 once |
| `GGML_CUDA_CPY_F16_VEC=1` | contiguous F32 to F16 copies use the vectorized converter |
| `GGML_CUDA_FUSE_NORM_F16=1` | `rms_norm * weight` writes that F16 input directly (fused into the norm kernel) |
| `KEV_PIPELINE=1` | branch round N+1 is decoded before the head of round N, whose rows stay in the other half of a double output buffer, so host work overlaps the GPU |

`KEV_TIMING=1`, `LLAMA_KEV_DECODE_TIMING=1` and `GGML_SCHED_KEV_REALLOC_LOG=1` log host-side phase times.

## Results on one V100-SXM2-32GB (Kev-9B, F16)

Against the reference PyTorch server on the same GPU:

| Case | PyTorch | This fork |
|---|---|---|
| 64 concurrent clients, short documents, 6 questions | 5 - 6.5 req/s, p95 10.3 s | 7.0 req/s, p95 9.6 s (`53bc2f051`) |
| 34 questions in one request (new / repeated document) | 0.92 s | 1.26 / 0.55 s |
| 96 questions in one request | 1.8 s | 1.74 s |
| 2.2k-token document, new / cached | 920 / 167 ms | 810 / 124 ms |
| 32k-token document | 17 s | 11.8 s |
| 60k-token document | out of memory | supported |

Later changes (`KEV_HTTP_PREP` through `GGML_CUDA_FUSE_NORM_F16` and `KEV_PIPELINE`) added about
12.5 % more with 64 clients in same-window A/B runs (6.31 to 7.10 req/s in that harness) and cut the GPU
idle time from 11.3 % to 4.5 %. Absolute req/s moves by several percent between windows, so each change was
judged against its control run alternately in the same window.

## How the changes were verified

- **Same answers as PyTorch**: every answer of a 172-question evaluation set identical, max |Δp| ≤ 0.0055
  (fp16 on both sides).
- **Exactness of each flag on CPU**: `tools/kev/parity_batch.py`, `parity_flags.py` and a byte-level A/B of full
  HTTP responses with the variable on and off, each with a control that must differ (for example a q8_0 KV
  cache) to show that the comparison discriminates. The pipelined mode was also mutation-tested (reading the
  wrong output half changes 21 of 39 responses).
- **On the GPU**: byte-level A/B of full responses with each variable on and off, `test-backend-ops` for every
  CUDA change (including the new `RMS_NORM_MUL_F16` case), then throughput alternated A/B/A/B.
